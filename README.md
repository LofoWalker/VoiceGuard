## Overview

VoiceGuard-Engine is a research-first anti-voice-spam core designed to detect
AI-generated callers during live phone conversations (*vishing*).

Instead of relying on phone-number reputation or blocklists, it analyzes the
audio stream itself to estimate, in real time, whether a caller sounds like a
genuine human or an AI-driven voice-phishing system. The engine runs locally —
no cloud inference call — which is both a privacy choice and a strict latency
requirement.

It is a pure-Kotlin/JVM library (no UI, no Android SDK in this phase), built so
it can be unit-tested on plain JVM CI and later embedded into an Android app.

> **Status:** active R&D. The detection core, orchestration, scoring, a 14-rule
> production pipeline, and an automated dataset-validation harness are all
> implemented. See [`CLAUDE.md`](CLAUDE.md) for the operational map of the code,
> [`architecture.md`](architecture.md) for design rationale and ADRs, and
> [`prd.md`](prd.md) for the product spec.

## Why this project exists

Publicly available text-to-speech and voice-conversion tools now make convincing,
interactive scam calls easy to automate. That breaks current call protection:

- Number-based filtering fails against spoofed or disposable lines.
- Human listeners miss subtle synthetic artifacts.
- Cloud analysis adds privacy, latency, and cost trade-offs.

VoiceGuard-Engine addresses the gap with local acoustic, prosodic, and behavioral
analysis performed directly on the device.

## Core idea

The engine continuously processes short (500 ms) audio chunks and combines many
independent detection rules into a single suspicion score. It exposes two live
indicators, updated every chunk:

- **Global Confidence** — how mature and reliable the analysis is over time.
  Monotonically non-decreasing; communicates *evidence accumulated*, not
  instantaneous certainty.
- **AI Probability** — the verdict, treated as meaningful only once confidence
  is high.

This split deliberately avoids a verdict gauge that flickers on every line
crackle: confidence gates the verdict.

The application is **strictly informative** — it computes scores and never
blocks, drops, or interrupts a call. The user keeps full control.

## How it works

A `DetectionOrchestrator` dispatches each chunk to all rules in parallel
(Kotlin Coroutines) and aggregates their results with a confidence-aware
weighted average:

```
aiProbability = Σ(score_i · weight_i · confidence_i) / Σ(weight_i · confidence_i)
```

A rule that lacks data returns `confidence = 0.0` and automatically excludes
itself from the calculation. State is exposed reactively through a
`StateFlow<DetectionUiState>`.

### Detection rules

The pipeline currently wires **14 production rules** spanning several signal
families — spectral artifacts, prosodic/emotional dynamics, jitter & shimmer,
cepstral peaks, micro-pause distribution, harmonic consistency, energy envelope,
room response, codec artifacts, speech entropy, noise linearity, and human
imperfection. Rule weights are calibrated from measured discriminative power
(AUC and Cohen's *d*) on the evaluation dataset and centralized in a single
`RuleWeightConfig`. A 15th rule, behavioral turn-taking latency, is implemented
but reserved for live conversational calls (isolated-utterance datasets have no
turn-taking). The full table lives in [`CLAUDE.md`](CLAUDE.md).

### Performance design (mobile constraints)

Three mechanisms keep CPU/battery use low on a target device (Pixel 9a class):

- **Early exit** — skip the costly spectral FFT when lightweight rules confirm
  organic human audio with full confidence.
- **Intermittent sampling** — suspend heavy rules during stable monologues and
  resume on the next transition (silence, speech turn, energy spike).
- **Injectable spectral classifier** — Phase 1 uses a pure-JVM FFT classifier
  behind `SpectralClassifierPort`, swappable for a TensorFlow Lite model in
  Phase 2 without touching domain code.

Target budget: ≤ 50 ms of processing per 500 ms chunk on the JVM.

## Architecture

Strict **hexagonal (ports & adapters)** layering. The `domain/` and `rules/`
layers are pure Kotlin/JVM — zero Android SDK, telephony, or native
dependencies — enforced at runtime by `DomainScopeComplianceTest`.

```
com/voiceguard/
├── domain/      model · port · service · context · dsp   (pure JVM core)
├── rules/       15 AudioDetectionRule implementations
├── adapters/    FftSpectralClassifier · DatasetAudioSource
└── harness/     ValidationRunner · WeightSweepRunner · RuleWeightConfig
```

See [`architecture.md`](architecture.md) for diagrams and the architecture
decision records (ADR-01..ADR-04).

## Build and run

Requirements: JDK 21, Gradle (wrapper included), Kotlin 2.0.21.

```bash
# Build and run unit tests
./gradlew build
./gradlew :voiceguard-engine:test

# Validate against a dataset → accuracy / FPR / latency + per-rule AUC report
./gradlew :voiceguard-engine:validateEngine -PdatasetPath=/path/to/dataset
./gradlew :voiceguard-engine:validateEngine -PdatasetPath=/path/to/dataset -Pverbose

# Recalibrate rule weights via random weight-space search
./gradlew :voiceguard-engine:sweepWeights -PdatasetPath=/path/to/dataset -PnRuns=200
```

On Windows use `gradlew.bat`.

**Dataset layout:** the root directory must contain `real/` (or `human/`) and
`fake/` (or `ai`/`deepfake`) subdirectories holding 16-bit mono WAV/MP3 files.
Files are resampled to a common 16 kHz to remove a sample-rate/label confound.

## Validation targets

Success is measured on open-source research datasets against the PRD KPIs:

- **Accuracy:** ≥ 85% on mixed human vs AI test data
- **False positive rate:** ≤ 5%
- **Latency:** ≤ 50 ms per 500 ms chunk on the JVM

Reference datasets: **Fake-or-Real (FoR), rerecorded** and HuggingFace
**Deepfake-Audio-Detection** sets. The engine currently sits below the accuracy
and FPR targets at the recall-favouring operating point — closing that gap with
better-calibrated rules, score calibration, and a realistic phone-call dataset is
the open R&D work tracked in [`todo.md`](todo.md). Run `validateEngine` to read
the current live numbers.

## Scope

**In scope (Phase 1, R&D and core engine):** Kotlin core architecture, reactive
coroutine/StateFlow orchestration, dynamic weighted scoring, confidence
accumulation over time, the rule pipeline, and the automated dataset-validation
harness.

**Out of scope (Phase 2):** Android UI (Jetpack Compose), real call-interception
plumbing, and full OS integration.

## Vision

VoiceGuard-Engine aims to be a practical local defense layer against modern voice
phishing — not to terminate calls automatically, but to provide a clear,
real-time trust signal that helps users judge whether a conversation feels
authentic or machine-generated.
